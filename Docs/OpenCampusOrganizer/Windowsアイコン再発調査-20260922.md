# Windowsのテーマアイコン再発調査

対象は0.4.5の「テーマを変更してもタスクバーとスタートメニューのアイコンが変わらない」という報告。調査元はmainの `f456eea`、外観の直前修正は `9c7e1e2`（PR #8）。

## 確認できた事実

- 0.4.5のインストール済みスタートメニューリンクは、実行中のEXEのアプリコット用リソース `-105` を参照していた。Shell APIで取り出した画像の内部色もアプリコットと一致した。したがって「テーマ要求が届かず、リンクの参照番号も変わっていない」だけでは今回の報告を説明できない。
- 0.4.5はリンクの保存と `SHCNE_UPDATEITEM` によるファイル変更通知を行うが、表示済み画像に対する `SHUpdateImage` は呼んでいない。
- プロセスとウィンドウに同じAppUserModelIDを設定している。ウィンドウのIDを空にしてから同じIDへ戻しても、その間はプロセスのIDを継承するため、実効IDの変更にはならない。[MicrosoftのAppUserModelID仕様](https://learn.microsoft.com/en-us/windows/win32/shell/appids) はこの優先関係を定義しているが、この操作によるアイコンキャッシュの再読込を保証していない。
- 既存テストの模擬ストアは「空にしたIDは別のIDになり、再設定で必ず画像を再取得する」と扱っていた。実際の継承動作を表しておらず、テストの成功からExplorerの表示更新を判断できなかった。実ウィンドウのテストも、主にプロパティ値とアイコンハンドルの存在を確認していた。

以上から、画像を保持するShell側への反映と、それを検証するテストに不足があると判断した。利用者が見ていたタスクバー／スタート画面の内部キャッシュや描画停止そのものを取得したわけではないため、全環境に共通する単一原因の断定とは区別する。

## 修正方針と実装

1. EXEに埋め込まれた5配色・各9サイズの画像を、再圧縮せずICOへ書き出す。保存先は `%LOCALAPPDATA%\OpenCampusOrganizer\appearance\icon-<SHA-256>.ico`。内容が同じなら同じファイルを再利用し、色や画像内容が違えば別の名前になる。
2. 一時ファイルへの書込とflushを終えてから最終名へ移す。公開済みファイルの上書きは行わず、再利用時も実際のバイト列を確認する。画像の参照を公開するのは保存成功後に限る。
3. 実行中EXEと起動先が一致する既存リンクの `IconLocation` と再起動アイコンをICOへ揃える。名前だけが同じ別アプリは変更せず、引数と作業フォルダーを保持する。インストーラーで同じリンクがEXE参照へ戻った場合も、次の起動・テーマ適用で再設定する。
4. 変更前の画像の場所・インデックスを取得し、保存後に [SHUpdateImage](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shupdateimagew) とリンク変更通知を送る。同じ色の再試行でも通知を再送する。プロセス・リンク・ウィンドウのアプリIDは固定する。

同じICOファイル名を上書きする試作では、別プロセスの通知受信側でも、画像リストに読み込み済みの旧色が残ることを観測した。この方式は採用せず、配色と内容ごとに不変のファイルを使う。テーマ切替ごとにランダムなファイルを増やす方式ではなく、同一の画像群なら最大5ファイルを再利用する。

旧バージョンの画像ファイルは、残っているショートカットが参照する可能性があるため、自動削除しない。このディレクトリは配色画像だけを保持する。Windows全体のキャッシュ削除、Explorerの再起動、ピン留めの追加・解除、アプリIDの切替、ウィンドウの隠蔽は行わない。

## 自動検証

既存のWindows CIが実行する `oco_appearance_test` に組み込む。

- 全5配色×9サイズについて、出力ICOと埋込画像の描画結果を比較。
- 配色ごとの異なるファイル名、同色再利用、読取専用でも変更不要な画像の再利用、破損ファイルの拒否、書込失敗と再試行。
- 同じリンクで5配色を3周し、`SHGetFileInfo` の画像リストと `IShellItemImageFactory` が返すアイコンの内部色を比較。アンチエイリアスによる輪郭の丸めは比較対象から除外。
- 実際の `SHCNE_UPDATEIMAGE` 通知を購読して受信を確認。プロパティの代入を通知受信の代わりにしない。
- 旧EXE参照からの移行、同名リンクのインストーラー相当の再作成、変更不要／変更が必要な読取専用リンク、別アプリの保全、引数・作業フォルダーの保持。
- 全5色のウィンドウ更新、同色再試行、DPI変更、Shell再初期化相当の再適用、最小化状態、不正なテーマ、解放。

テスト用AppUserModelIDと一時保存先を製品から分離し、インストール済みアプリのタスクバーグループ・配色画像を変更しない。Flutterの非同期競合テストも引き続き実行する。

## 検証結果と残る確認

ローカルのWindows（ビルド26200.9457）で上記ネイティブテスト、Flutter 202件、静的解析、Dartフォーマット検証、CI判定・公開処理の21件が成功した。`SHUpdateImage` の呼出しだけを一時的に除いた検証では、`No image invalidation reached the shell consumer` でテストが失敗することも確認し、通知欠落を検出できることを確かめた。この一時変更は元に戻している。

0.4.7+16のWindows Releaseビルド、インストーラー作成、配布ペイロード検査、通知処理を戻したネイティブテストの再実行も成功した。インストーラーの作成はインストールや公開を意味しない。実行ログは作業ディレクトリの `artifacts/theme-icons` に保存する。最終コミットのクリーン環境でのWindowsビルド・導入検証は、PRのChecksも参照する。

自動テストの画像取得はWindows APIによるもので、タスクバーやスタート画面のスクリーンショット比較ではない。既存ピン留めあり／なし、Windows 11のスタートのピン留めと全アプリ一覧、0.4.5からの実アップデート後の表示、実際のExplorer再起動後の表示は配布前の手動確認事項として残す。実ユーザーの稼働中アプリや保存設定は、この検証のために終了・置換・初期化しない。

## 0.4.7公開後の再発と追加修正候補

0.4.7+16を導入した環境でも、タスクバーとスタートの両方で未反映との報告があった。追加の診断通知を試した後には「ダークに変えてからタスクバーがダークで固定され、スタートは変わらない」との報告を受けた。診断通知の途中で利用者がテーマを変更しているため、どの単独通知がタスクバーへ効いたかは断定しない。

実行中の0.4.7で、ウィンドウの大小アイコン、RelaunchIconResource、インストール済みスタートメニューリンク、`shell:AppsFolder` のアプリ項目から取得する32・48・256pxの画像が選択色へ更新されることを確認した。新規取得した画像が正しくても、表示済みのShell UIが再取得するとは限らない。

コードでは `WM_SETICON` が再起動アイコン情報の更新より先に発行され、リンクの更新通知もウィンドウの情報が揃う前に届いていた。さらに、表示側が画像を取り直すための全体通知は製品に含まれておらず、診断時に一度呼んでも以後のテーマ選択には連動しなかった。

追加候補では、リンクの保存・COM解放、ウィンドウのプロパティ更新、大小アイコン更新を先に完了させる。その後で `SHCNE_ASSOCCHANGED`、各リンクの `SHCNE_UPDATEITEM`、登録されている場合のAppsFolder項目更新を順に送る。テーマ適用と同色の再試行で毎回実行し、DPI変更では実行しない。Windows全体のキャッシュファイルを削除する処理ではないが、他のデスクトップアイコンも再描画される場合がある。

通知順序は [MicrosoftのSHChangeNotify仕様](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shchangenotify) と [ChromiumのWindows 11対応](https://github.com/chromium/chromium/blob/main/chrome/browser/profiles/profile_shortcut_manager_win.cc) を参照した。COM解放は通知時に再読込できるようにする予防措置で、今回の単独原因として観測したものではない。

### 追加の自動検証と表示確認

- 実ウィンドウをサブクラス化し、`WM_SETICON` を受ける瞬間に新色のRelaunchIconResourceが既に設定されていることを確認する。
- 通知のコールバックで、その時点のウィンドウの画像・プロパティ、全体通知→リンク通知の順序、別のShellLinkオブジェクトから新しいアイコン参照を再読込できることを確認する。
- 全5色の3周と同色再試行で全体通知を要求し、DPI変更・無効テーマでは要求しないことを確認する。
- 通常の自動テストは全体通知を記録するだけにし、利用者のデスクトップ全体を繰り返し更新しない。個別のテスト用リンク通知と画像取得には実際のShell APIを使う。

この候補は、実表示の修復確認が完了するまでDraftとして扱う。受け入れ条件は、テーマを固定して色を見比べ、ダーク→白・青→ウォームグレー→セージ→アプリコット→ダークを3周しても、タスクバー・スタートのピン留め・全アプリ一覧の表示が追従すること。既存のピン留めとアップデート後のリンクでも確認する。通知の配送、画像APIの成功、テストの合格だけで「再発解消」と記録しない。

追加後のローカル検証では、ネイティブテスト、Flutter 202件、静的解析、97ファイルのDartフォーマット検査、CI用Python 21件が成功した。`WM_SETICON` を旧順序へ戻す変異では `Shell read a partially published theme`、全体通知を省く変異では `Theme or retry omitted shell cache refresh` により失敗し、修正を戻すと成功した。0.4.8+17のWindows Releaseビルドとインストーラー作成、18ファイルの配布ペイロード検査も成功。稼働中アプリの置換・公開は行っていない。

### スタートの一覧とピン留めの追加切り分け

利用者からタスクバーがセージグリーンになったとの確認を受けた。一方、スタートのアプリ一覧に直接表示されるOCは未反映のままだった。「ピン留めだけ更新された」という途中の回答は利用者が訂正し、通知だけでは変わっていない。その後、利用者が新しくピン留めしたOCはグリーンになった。これは新規ピン留め時の1回の確認であり、既存ピン留めの自動更新や、その後のテーマ切替の成功を意味しない。

対象のユーザー用リンクは1個で、起動先、アイコン参照、アプリIDは正しかった。次の追加診断でも、利用者が確認したアプリ一覧は変わらなかった。

- リンクの更新日時を変更し、リンク・親フォルダー・AppsFolderに更新を通知。
- バックアップを作成してから、バイト列が同じリンクを同じパスへ原子的に置換して更新を通知。置換前後とバックアップのSHA-256が一致し、ファイルIDは変わり、アプリIDと登録項目は維持された。

これらの処理は表示改善を確認できなかったため、製品には追加していない。ピン留めの解除・再作成、ExplorerやStartMenuExperienceHostの再起動、Windowsのキャッシュファイル削除も製品の処理には含めない。

### インストーラー由来の文字列形式を扱う修正

実際のリンクのAppUserModelIDは `VT_BSTR`、再起動アイコン参照は `VT_LPWSTR` だった。従来の比較は `VT_LPWSTR` しか読まないため、正しいIDが保存されていても空として扱い、変更不要なリンクまで再保存しようとしていた。同じ値を別の型で `SetValue` しても、ShellLinkは元の文字列形式を保持することを実ファイルで確認した。

文字列の比較は `VT_BSTR` と `VT_LPWSTR` をともに読み取り、取得失敗や文字列以外の値は一致扱いにしない。[MicrosoftのPropVariantToStringAlloc仕様](https://learn.microsoft.com/en-us/windows/win32/api/propvarutil/nf-propvarutil-propvarianttostringalloc) に従って文字列を取得・解放する。

回帰テストは、初めから `VT_BSTR` のIDを持つインストーラー相当の実リンクと、アプリが `VT_LPWSTR` でIDを追加するリンクを並べて全5色を3周する。同色の再試行では、どちらのリンクも読み取り専用のまま成功し、更新日時が変わらないことを確認する。変更が必要な読み取り専用リンクの失敗と、書込可能に戻した後の回復も継続する。修正前には `Unchanged BSTR read-only shortcut should succeed` で失敗し、修正後には成功した。

この修正は不要な書込と誤った失敗判定を解消する。スタートのアプリ一覧が古い画像を表示する直接原因と確認できたものではないため、表示問題の解決とは別に記録する。
