# Windowsのテーマアイコン再発調査

対象は0.4.5の「テーマを変更してもタスクバーとスタートメニューのアイコンが変わらない」という報告。調査元はmainの `f456eea`、外観の直前修正は `9c7e1e2`（PR #8）。

## 確認できた事実

- 0.4.5のインストール済みスタートメニューリンクは、実行中のEXEのアプリコット用リソース `-105` を参照していた。Shell APIで取り出した画像の内部色もアプリコットと一致した。したがって「テーマ要求が届かず、リンクの参照番号も変わっていない」だけでは今回の報告を説明できない。
- 0.4.5はリンクの保存と `SHCNE_UPDATEITEM` によるファイル変更通知を行うが、表示済み画像に対する `SHUpdateImage` は呼んでいない。
- プロセスとウィンドウに同じAppUserModelIDを設定している。ウィンドウのIDを空にしてから同じIDへ戻しても、その間はプロセスのIDを継承するため、実効IDの変更にはならない。[MicrosoftのAppUserModelID仕様](https://learn.microsoft.com/en-us/windows/win32/shell/appids) はこの優先関係を定義しているが、この操作によるアイコンキャッシュの再読込を保証していない。
- 既存テストの模擬ストアは「空にしたIDは別のIDになり、再設定で必ず画像を再取得する」と扱っていた。実際の継承動作を表しておらず、テストの成功からExplorerの表示更新を判断できなかった。実ウィンドウのテストも、主にプロパティ値とアイコンハンドルの存在を確認していた。

以上から、画像を保持するShell側への反映と、それを検証するテストに不足があると判断した。利用者が見ていたタスクバー／スタート画面の内部キャッシュや描画停止そのものを取得したわけではないため、全環境に共通する単一原因の断定とは区別する。

## 修正方針と実装

1. EXEに埋め込まれた5配色・各9サイズの画像を、再圧縮せずICOへ書き出す。保存先は `%LOCALAPPDATA%\OpenCampusOrganizer\appearance\icon-<SHA-256>.ico`。内容が同じなら同じファイルを再利用し、色や画像内容が違えば別の名前になる。
2. 一時ファイルへの書込とflushを終えてから最終名へ移す。公開済みファイルの上書きは行わず、再利用時も実際のバイト列を確認する。画像の参照を公開するのは保存成功後に限る。
3. 実行中EXEと起動先が一致する既存リンクの `IconLocation` と再起動アイコンをICOへ揃える。名前だけが同じ別アプリは変更せず、引数と作業フォルダーを保持する。インストーラーで同じリンクがEXE参照へ戻った場合も、次の起動・テーマ適用で再設定する。
4. 変更前の画像の場所・インデックスを取得し、保存後に [SHUpdateImage](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shupdateimagew) とリンク変更通知を送る。同じ色の再試行でも通知を再送する。プロセス・リンク・ウィンドウのアプリIDは固定する。

同じICOファイル名を上書きする試作では、別プロセスの通知受信側でも、画像リストに読み込み済みの旧色が残ることを観測した。この方式は採用せず、配色と内容ごとに不変のファイルを使う。テーマ切替ごとにランダムなファイルを増やす方式ではなく、同一の画像群なら最大5ファイルを再利用する。

旧バージョンの画像ファイルは、残っているショートカットが参照する可能性があるため、自動削除しない。このディレクトリは配色画像だけを保持する。Windows全体のキャッシュ削除、Explorerの再起動、ピン留めの追加・解除、アプリIDの切替、ウィンドウの隠蔽は行わない。

## 自動検証

既存のWindows CIが実行する `oco_appearance_test` に組み込む。

- 全5配色×9サイズについて、出力ICOと埋込画像の描画結果を比較。
- 配色ごとの異なるファイル名、同色再利用、読取専用でも変更不要な画像の再利用、破損ファイルの拒否、書込失敗と再試行。
- 同じリンクで5配色を3周し、`SHGetFileInfo` の画像リストと `IShellItemImageFactory` が返すアイコンの内部色を比較。アンチエイリアスによる輪郭の丸めは比較対象から除外。
- 実際の `SHCNE_UPDATEIMAGE` 通知を購読して受信を確認。プロパティの代入を通知受信の代わりにしない。
- 旧EXE参照からの移行、同名リンクのインストーラー相当の再作成、変更不要／変更が必要な読取専用リンク、別アプリの保全、引数・作業フォルダーの保持。
- 全5色のウィンドウ更新、同色再試行、DPI変更、Shell再初期化相当の再適用、最小化状態、不正なテーマ、解放。

テスト用AppUserModelIDと一時保存先を製品から分離し、インストール済みアプリのタスクバーグループ・配色画像を変更しない。Flutterの非同期競合テストも引き続き実行する。

## 検証結果と残る確認

ローカルのWindows（ビルド26200.9457）で上記ネイティブテスト、Flutter 202件、静的解析、Dartフォーマット検証、CI判定・公開処理の21件が成功した。`SHUpdateImage` の呼出しだけを一時的に除いた検証では、`No image invalidation reached the shell consumer` でテストが失敗することも確認し、通知欠落を検出できることを確かめた。この一時変更は元に戻している。

0.4.7+16のWindows Releaseビルド、インストーラー作成、配布ペイロード検査、通知処理を戻したネイティブテストの再実行も成功した。インストーラーの作成はインストールや公開を意味しない。実行ログは作業ディレクトリの `artifacts/theme-icons` に保存する。最終コミットのクリーン環境でのWindowsビルド・導入検証は、PRのChecksも参照する。

自動テストの画像取得はWindows APIによるもので、タスクバーやスタート画面のスクリーンショット比較ではない。既存ピン留めあり／なし、Windows 11のスタートのピン留めと全アプリ一覧、0.4.5からの実アップデート後の表示、実際のExplorer再起動後の表示は配布前の手動確認事項として残す。実ユーザーの稼働中アプリや保存設定は、この検証のために終了・置換・初期化しない。
