# 0.4.1の履歴・抽出の性能検証

Issue #21、#27、#32を対象に、PR #31取り込み後の `c84a77f7e13b5431a2734ecef9a0b7edf1451a31` と比較した。生の測定値は [履歴性能測定-0.4.1.json](履歴性能測定-0.4.1.json)。2026年9月8日、Windows 11、Dart 3.12.2 / Flutter 3.44.4で、実ユーザーのデータ・Token・Discord接続を使わずに実施した。

## 変更内容

- `OperationRows` は最大32行の葉と経路だけを更新する不変の木。1人の更新で全員分の参照をコピーしない。成否件数は節点に保持し、UIの集計は成否1種類につきO(1)。Journalは同じ節点を飛ばし、変更行だけを追記する。
- 送信前のinFlight、送信後の結果の保存とflushは維持する。保存例外で後続を止め、未確認の人は再開時にDiscordの現在状態を照合する。旧スナップショットは更新しない。
- 履歴一覧は初回30件の要約だけを取得し、必要な分を追加取得する。詳細は選択した1件だけを読み、起動時に全レポートをControllerへ保持しない。書込キャッシュは操作1件までで、完了・保存失敗時に解放する。
- スマホからの抽出は `retainMessages: false` で投稿単位の結果を保持しない。この場合だけ最小投稿数未満の投稿者のメンバー照会を省く。重複検査用の投稿IDと集計値は保持し、走査制限や権限確認は省かない。PCと旧形式の再開条件は保持ありのまま。

## 実ファイルでの履歴読み込み

1履歴につき架空の500人。データ作成と読み込みは別プロセスで行い、読み込み側の最大RSSに作成時の保持量を混ぜない。新方式は索引生成済みの通常起動を測定した。旧版は全件の詳細、新版は最初の30要約を開くという、実際の一覧表示経路の比較である。

| 履歴数 | 旧: 原本の読込件数 | 新: 原本 / 要約の読込件数 | 旧 / 新の時間 | 旧 / 新の最大RSS（bytes） | 旧 / 新の保存量（bytes） |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 0 / 1 | 26.8 / 17.5 ms | 195,506,176 / 234,516,480 | 137,139 / 81,027 |
| 100 | 100 | 0 / 30 | 166.2 / 37.9 ms | 241,868,800 / 233,594,880 | 13,758,990 / 8,100,594 |
| 1,000 | 1,000 | 0 / 30 | 1,295.3 / 71.5 ms | 374,366,208 / 233,984,000 | 138,085,890 / 81,008,694 |

新方式は表のほかに設定・索引を各1回読み、ファイル名を列挙する。索引のID・日時・終了状態は履歴数に比例して保持する。古い版からの初回移行や索引破損時には全原本を1件ずつ読んで派生索引を作るため、この通常起動の値は当てはまらない。未完了の記録は起動ごとに原本で再照合する。

RSSにはVM/JITの初期費用も含む。1履歴では新版の最大RSSが増えており、すべての条件でメモリが減るとは評価しない。保存量の差は主に既定のCSV二重保存をやめたためであり、履歴原本を削除・圧縮した結果ではない。

## 実ファイルでのロール操作

同じ架空Gatewayと実際の `OperationService` / `StoredOperationJournal` を使い、FileLocalStoreで保存した。旧ソースにも同じファイルI/Oを配置し、ディスクへのflush条件を揃えた。通信待ち・Discordのレート制限を含まない。

| 人数 | 旧 / 新の全体時間 | 旧 / 新のUI集計時間（全スナップショット合計） | 旧 / 新の追記回数 |
|---:|---:|---:|---:|
| 500 | 5.59 / 7.17 秒 | 12.690 / 3.247 ms | 1,001 / 1,001 |
| 1,000 | 10.54 / 14.46 秒 | 42.661 / 4.249 ms | 2,001 / 2,001 |
| 10,000 | 100.87 / 101.94 秒 | 3,952.074 / 8.542 ms | 20,001 / 20,001 |

新方式は初期原本・要約・索引等の置換書込6回、旧方式は初期原本と終了CSVの2回を別途行う。各条件1回の測定で、ディスクとOSの変動を含む。今回、全体時間の短縮は確認できていない。集計とコピーのCPU負荷を減らしても、送信前後の安全な保存は残る。

スナップショットだけの別プロセス測定では、旧 `List.unmodifiable` と7種類の全行集計を、新しい経路共有・OperationReport・集計と比較した。

| 人数 / スナップショット数 | 旧 / 新の構築時間 | 旧 / 新の7種類集計時間 |
|---:|---:|---:|
| 500 / 1,000 | 2.110 / 3.637 ms | 9.952 / 0.833 ms |
| 1,000 / 2,000 | 6.373 / 5.148 ms | 35.003 / 1.135 ms |
| 10,000 / 20,000 | 434.573 / 21.060 ms | 3,346.741 / 1.647 ms |

旧・新で成否件数のチェックサムが一致した。これはDart VMの合成CPU測定で、Flutterの描画フレーム時間ではない。500人の構築単独では木の更新費用が上回る。

## 保存方針

| 候補 | 採用方針と理由 |
|---|---|
| 件数・日数・容量で自動削除 | 採用しない。過去の業務記録や未確認対象を消す可能性がある |
| 自動アーカイブ | 今回は採用しない。復元先・検索方法・利用者の保持方針が必要 |
| 原本の圧縮・イベントの間引き | 今回は採用しない。schema 1と追記末尾の復旧を保ち、書込の原本はそのままにする |
| 派生CSVの必要時再生成 | 採用。PC・タブレットの「結果CSVを出力」で履歴から再生成する |
| CSVの自動バックアップ | 設定で選択可能。初期オフ。オン以降の操作では従来どおり内部保存する |

既存の履歴・CSVを移動・削除しない。CSVの自動保存をオフに戻しても過去CSVは残る。保存容量の上限は設けていないため、原本は利用とともに増える。設定・履歴の一括初期化やアンインストール時の削除は、従来どおり利用者が選択したときだけ行う。未完了/inFlight/uncertainの原本、承認済み再開タスクはCSVの設定と独立して保存する。

索引は原本の保存後に更新する派生データ。旧形式・派生索引欠落・破損は原本から再構成する。途中で切れた最終行は採用せず、途中の破損や未知の原本schemaはエラーにする。索引更新で失敗した場合も原本を保管し、再起動時に復元する。

## 再現手順と回帰検証

`Source/OpenCampusOrganizer` で実行する。保存先には未作成の測定専用ディレクトリを指定する。ベンチマークは作成したファイルを自動削除しない。

```powershell
dart run tool/journal_benchmark.dart operations 1000 C:/temp/oco-measure-operations-new
dart run tool/journal_benchmark.dart seed 1000 C:/temp/oco-measure-history-new
# seedとは別プロセスで実行
dart run tool/journal_benchmark.dart history indexed C:/temp/oco-measure-history-new
dart run tool/snapshot_benchmark.dart baseline 10000
dart run tool/snapshot_benchmark.dart current 10000
```

旧ファイルI/O比較は、上記基点の `lib` を別ディレクトリへ展開し、現版の `tool/journal_benchmark.dart` と `lib/core/platform/file_store.dart` を同じ相対位置に置く。旧版の履歴読込だけ `history legacy` を指定する。依存パッケージや認証情報は不要。

回帰テストは `operation_rows_test.dart`、`history_storage_test.dart`、`history_layout_test.dart`、`extraction_retention_test.dart` を追加した。1,000履歴の30件取得、詳細1件の読込、65件の画面ページ送り、非表示詳細を読まないこと、旧schema移行、破損末尾、保存失敗、再起動、実ファイルでの送信前flush、旧スナップショットの不変性を確認した。既存の再開・権限・取消・CSV・モバイル表示テストも含め、Flutter 189件が成功した。
