# OCO追加レビュー: 通信・保存の安全性

## 対象と方法

基準コミットは `9c7e1e22096fa423fe576ac7a8aa9f840ed686f3`（0.4.5）。PR #9で対応する。

OCOの通信層、設定・履歴の保存、ロール操作の承認・権限照合、抽出上限、処理中止・再開、Windowsのトレイ処理、Androidの通知・サービス、iOSの起動・通知経路、CSV共有を対象にソースを確認した。すべてのファイルを網羅する侵入テストや、依存パッケージ全件の脆弱性監査ではない。

外部Discordへの実更新や利用者のToken・履歴へのアクセスは行わない。HTTP検証は偽クライアント、保存検証は専用の一時ディレクトリを使う。

## 修正した問題

| 問題 | 前提と影響 | 対応 |
| --- | --- | --- |
| 同一Tokenでの再接続を旧接続と区別できない | 通信層に待機・実行中の要求が残る状態で切断・再認証すると、古い要求や読取結果が有効と判定される。通常画面のbusy制御とは別に通信層の境界を保護する必要がある | 接続世代を取得時・送信前後・再試行時に検証。送信済み更新の確定した成功応答は記録用に保持 |
| 最終429で次の要求への制限が失われる | 再試行上限に到達した直後の別要求が、最後のRetry-Afterを待たずに送信される | 待機期限をルート・globalへ登録した後で要求を終了 |
| 応答本文の取得が無制限 | 大きな応答で本文を全量蓄積してから解析していた。資源枯渇への防御不足であり、リモートからの悪用を実証したという意味ではない | Content-Lengthと実受信量を検証。既定8 MiB/応答。超過は中断し、機密本文を表示せず、再試行しない |
| 同じキーへのI/Oの競合 | 同じストアで連続する非同期書込み・追記が逆転し、後の状態が消える可能性がある | キー単位で読取・書込・追記を直列化。失敗は呼出し元へ返す一方、次の要求を停止しない |
| 予測可能な一時ファイルのリンク追跡 | アプリ保存領域へ事前にリンクを配置できるローカル主体が前提。リンク先のファイルを上書きしうる | 128ビットのランダム名と排他的作成を採用。既存の固定一時パスを開かず、自分の一時ファイルだけを削除 |

さらに、待機中に呼出し元が変更できたクエリをスナップショット化し、破棄後の再認証を拒否した。

## 再現証拠

製品コードを変更する前に7件のテストを追加したコミット `e6c852c93f8b17215985c142c1cb8ec4f1d9640f` をCIで実行した。

[修正前のCI #26](https://github.com/nononoyuyuyu/OC_Operational_Tools/actions/runs/34366125822/job/102515260424) では、フォーマットと静的解析が成功し、既存202件が成功、追加7件が想定箇所で失敗した。古いPUT・GET・再試行GETの受理、最終429後の間隔0秒（ルート別とglobal）、保存処理の逆転、リンク先の内容変更を確認した。修正後もこの7件を削除・緩和せず実行する。

追加検証では、応答サイズの境界、Content-Lengthの欠落・過少・過大、受信中断、送信済み更新の結果保持、再接続と並列読取、クエリの固定、保存・追記・読取順、別キーの独立性、失敗後の回復、一時ファイルの後片付け、CSVの拡張子を扱う。最終HEADでの結果はPR #9のCI結果欄に記録する。

## 維持する仕様と限界

- HTTPSの固定送信先、リダイレクト拒否、HTTP例外本文の非公開、ロールの承認・階層チェック、送信前の記録、既存データ形式・Token保管先は維持する。
- 応答上限は1応答あたりの受信バイト数であり、JSON展開後や複数応答を合わせたプロセス全体のメモリ上限ではない。通常のDiscord利用者が直ちにこの上限を悪用できると実証したものでもない。
- 保存順序はFileLocalStoreの同一インスタンス・同一キーに対する保証。複数アプリプロセス間の履歴トランザクションや、同じ権限で保存領域を継続的に改変できる攻撃者への完全防御は提供しない。OSのアクセス権を前提とする。
- 一時ファイルは既存アンインストーラーが認識する英小文字・数字・アンダースコアの名前と `.data.tmp` / `.csv.tmp` 形式を使う。正常な保存データや任意の別名ファイルを削除対象へ追加しない。
- CIはWindows・Android・iOSのビルド、Windowsネイティブ試験、Androidエミュレーター試験を使う。Windows・macOSの実ファイルI/O試験も追加する。macOS上のDart試験はiOS実機のサンドボックス試験ではない。利用者端末の目視確認、Webビルド、第三者による侵入テストは別の検証である。
